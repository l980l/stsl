# 우리 게임 — 현재 모디파이어 적용 분석

> 리서치 일시: 2026-05-22
> 리서치 방법: 코드베이스 탐색

## 요약

데미지 계산은 `autoload/battle_manager.gd` 한 파일에 흩어져 있으며, 단일 통합 파이프라인이 없다. 영웅 카드 데미지는 `_apply_card_effects`(L1008~)에서, 적 공격 데미지는 `_resolve_enemy_intent` 계열(L2180~)에서, 치명타는 `_roll_crit_damage`(L2498~)에서, 방어/취약/방어모드 등 "받는 쪽" 모디파이어는 `_deal_damage_to_enemy`(L1692~) / `_deal_damage_to_hero`(L1742~)에서 각각 적용된다.

핵심 문제: **합연산(flat)은 strength·bonus_per_hit·counter_pool 정도뿐이고, 나머지 모디파이어(strength 배율·weak·vulnerable·crit·marked·황제의무도·초원의결투사·방어모드·내성)가 전부 곱연산(`int(dmg * 배율)`)으로 별도 라인에서 순차 적용**된다. 곱들이 서로 독립 라인이라 곱끼리 누적되며, 특히 `치명타(×2~3) → 취약(×1.5) → 황제의무도(×1.25) → marked(치명타 확률로 흡수) → 방어모드 해제 시` 경로에서 수치가 폭증한다. 또한 strength조차 `dmg * (1.0 + 0.1*str)`로 곱연산이라, 동일 strength라도 기본 데미지가 큰 카드에서 비선형적으로 커진다.

`int()` 절삭이 각 곱 단계마다 끼어 있어 순서에 따라 1~2 데미지 오차도 발생한다.

### 2. 합연산 vs 곱연산 정리

**합연산(flat add)인 것 — 소수:**
- `power.strength_player` (영웅): `dmg += value` — `battle_manager.gd:1046`, `1673`
- `power.bonus_per_hit`: 별도 데미지 인스턴스로 발사 — `battle_manager.gd:1066-1067`, `1080-1081`
- `power.every_nth_attack_bonus`: 별도 인스턴스 — `battle_manager.gd:1095-1102`
- `counter_pool` (적): `dmg += counter_pool` — `battle_manager.gd:2195`
- block: `min()` 흡수 차감 — `battle_manager.gd:1709-1711`, `1775-1778`

**곱연산(multiplicative)인 것 — 대부분:**
- strength (적): `int(dmg * (1.0 + 0.1*str))` — `battle_manager.gd:2184` (※ 영웅 strength는 합, 적 strength는 곱 — 불일치)
- weak: `int(dmg * 0.75)` — `battle_manager.gd:1044`, `2186`
- vulnerable: `int(amount * 1.5)` — `battle_manager.gd:1701`(적), `1749`(영웅)
- 치명타: `int(base_dmg * crit_mult)` — `battle_manager.gd:2512`
- 황제의 무도: `int(dmg * 1.25)` — `battle_manager.gd:1061`, `1075`
- FORM_SWITCH offense ×1.5 / defense ×0.5 — `battle_manager.gd:2189`, `1704`
- dynamic_resistance ×0.2 — `battle_manager.gd:1708`
- double_next_damage ×2 — `battle_manager.gd:862`, `867`
- counter_pending ×0.5 — `battle_manager.gd:1753`

**적용 순서 (영웅 카드 → 단일 적 치명타 경로):**
1. `dmg = effect.value` — `battle_manager.gd:1041`
2. weak ×0.75 — `1044`
3. `+= strength_player` (합) — `1046`
4. (hit 루프) crit 판정·배율 — `_roll_crit_damage` 진입 `1072`
   - 내부: `int(base_dmg * crit_mult)` — `2512`
5. 황제의 무도 ×1.25 — `1075`
6. `_deal_damage_to_enemy(_sgl_dmg, ...)` 호출 — `1079`
7. double_next_damage ×2 — `1699`
8. vulnerable ×1.5 — `1701`
9. defense 모드 ×0.5 — `1704`
10. dynamic_resistance ×0.2 — `1708`
11. block 차감 — `1709-1711`

→ 즉 한 번의 공격이 **최대 6개의 독립 곱 라인**(crit, 황제무도, dnd, vulnerable, 모드, 내성)을 거치며, 각 단계가 `int()`로 절삭된다.

### 3. 곱연산 연쇄로 수치가 폭증하는 구체 경로

`battle_manager.gd:1072-1079` → `_roll_crit_damage`(2512) → `_deal_damage_to_enemy`(1699-1701)

**최악의 단일 타겟 공격 시나리오** (영웅 무사시 + 칭기즈칸 + 나폴레옹 동시 생존, 적이 marked·취약·반함):
- base = `effect.value` (예: 20)
- weak 없음 → 20
- strength_player +5 → **25** (합, 여기까지는 정상)
- crit: 초원의 결투사 → `crit_mult = 3.0` (`2511`), marked로 확률 +30% (또는 독날로 100%) → `25 × 3 = 75` (`2512`)
- 황제의 무도: 취약 적 → `75 × 1.25 = 93` (`1075`)
- `_deal_damage_to_enemy` 진입 → vulnerable: `93 × 1.5 = 139` (`1701`)
- (double_next_damage까지 묶이면) `139 × 2 = 278` (`1699`)

→ base 20이 **278까지** = 약 13.9배. 곱 배율들의 곱: `3.0 × 1.25 × 1.5 × 2.0 = 11.25배`, 여기에 strength 합산분이 base에 먼저 더해져 추가 증폭.

**폭증의 구조적 원인:**
- crit·황제무도·vulnerable·dnd가 **서로 다른 함수의 서로 다른 라인**에서 각자 `dmg = int(dmg * k)` 한다. 어느 것도 "이미 적용된 배율"을 인지하지 못한다.
- 설계상 marked는 "치명타 확률 +30%"인데, crit이 발동하면 marked가 곧 crit 배율(×2~3) 전체를 끌어오므로 사실상 marked = 강력한 곱 모디파이어로 작동한다(`2503` → `2512`).
- 영웅 strength만 합(`1046`)이고 적 strength는 곱(`2184`)이라, 같은 "strength"라는 이름의 스탯이 진영에 따라 스케일링 곡선이 다르다.

### 5. 합연산 후보 vs 곱연산 유지 후보 (코드 관점 의견)

#### 합연산으로 묶을 후보

- **공격자 측 증폭(outgoing) 통합**: weak·strength·crit·황제의무도는 모두 "공격자가 내보내는 데미지"를 키우는 모디파이어다. 현재 4개 라인에 흩어진 곱을 하나의 "additive bonus pool"로 묶을 수 있다. 예: `final = base * (1 + Σ(bonus_pct))`. crit을 `+100%`, 황제무도를 `+25%`, marked를 별도 `+30%`로 합산하면 `3.0×1.25 = 3.75배` → `1+1.0+0.25+0.3 = 2.55배`로 폭증이 크게 완화된다.
- **영웅 strength**: 현재 `dmg += value`(합). 적 strength(`dmg * (1+0.1·str)`, 곱)와 통일 필요. 둘 다 합산 풀에 `0.1·str` 비율로 넣거나, 둘 다 플랫으로 통일하는 게 일관적이다. 현 상태는 같은 이름의 스탯이 진영별로 다르게 동작하는 명백한 버그성 불일치다.
- **황제의 무도(+25%)·marked(+30%)**: 이름 자체가 "+X%"인 가산형 표현이므로 곱이 아니라 가산 풀에 넣는 것이 설계 의도에 맞다.

#### 곱연산으로 남길 후보

- **vulnerable(×1.5) — 받는 쪽 모디파이어**: "타겟이 받는 모든 피해"를 키우는 디버프. 공격자 증폭 풀과는 의미축이 다르므로 별도 곱 단계(`outgoing_pool` 적용 후 `incoming` 곱)로 유지하는 게 깔끔하다. 단 다른 incoming 모디파이어와는 가산으로 묶을 수 있다.
- **방어 모드(×0.5) / dynamic_resistance(×0.2) / counter_pending(×0.5) / invuln(0)**: 데미지 경감 계열. 경감은 곱연산이라야 "여러 경감이 곱해져 0으로 수렴"하는 자연스러운 거동이 나온다(합연산이면 경감 합이 100% 초과 시 음수 데미지 위험). 곱 유지가 타당.
- **double_next_damage(×2)**: "다음 공격 1회 2배"라는 명시적 ×2 메커니즘. 단발성 곱으로 유지하되, 공격자 증폭 풀의 가장 바깥에 적용할지 안쪽에 적용할지를 명문화해야 한다(현재는 `_deal_damage_to_enemy` 진입 직후, vulnerable보다 먼저 — L1699).
- **치명타**: 곱으로 둘지 가산 풀에 `+100%`로 넣을지는 밸런스 결정. 곱으로 두더라도 "황제의무도·marked는 가산, crit만 곱"으로 분리하면 폭증이 `11.25배 → 3.0×1.55 ≈ 4.65배` 수준으로 줄어든다.

#### 구조 개선 권고

현재 데미지 계산이 `_apply_card_effects`·`_resolve_enemy_intent`·`_deal_damage_to_enemy`·`_deal_damage_to_hero`·`_roll_crit_damage` 5곳에 분산돼 동일 모디파이어(weak·vulnerable)가 중복 구현돼 있다. `DamageContext` 같은 구조체를 만들어 `outgoing_flat / outgoing_pct_pool / crit / incoming_pct_pool / reduction_mult` 단계를 단일 함수로 통과시키는 파이프라인화를 권장한다. 부수적으로 단계별 `int()` 절삭도 마지막 1회로 줄여 절삭 오차를 제거할 수 있다.
