- 이번 조사 기준 HEAD는 `e900b444ffee9e4363832186eb612ee88a69cd7c`이며 미커밋 봇·평가기·위키와 미추적 아트가 있는 상태다. 이 작업은 게임 코드·게임 수치·기존 작업을 수정하거나 체크아웃·스태시·리셋하지 않았다. 새 측정은 `/tmp/STSL-portfolio-audit-b2R3kp`와 별도 `user://`에서 실행했다.
- **[당시 실측]** 당시 엔진이 기록한 값. **[당시 시뮬레이션]** 고정 조건에서 선택기/전투를 실행한 값. **[이번 재계산]** 기존 숫자로 계산한 개선율 또는 원시 시퀀스 재집계. **[오늘 신규 측정]** 오늘 새로 실행한 결과. **[코드 산출]** 코드 경로·설정에서 계산한 값으로 실행 측정과 다르다. **[미측정]** 주장할 수 없는 항목.
- 아래 개선율은 모두 **이번 재계산**이다. 시간·횟수 감소율은 `(이전−이후)/이전×100`. 시간비는 `이전시간/이후시간`이며 FPS 배수가 아니다. 비율 간 차이는 `%p`, 상대 감소는 `%`로 구분한다. 이후가 0이면 감소율은 계산할 수 있어도 나눗셈 기반 ‘무한 배 빨라짐’은 쓰지 않는다.
- 옛 성능 JSON은 개별 20회/5회 샘플 대신 **count·분위수·최댓값 요약만 보존**한다. 수록된 p50·p95는 읽어 검증했지만 원시 시간 배열이 없어 분위수·신뢰구간을 독립적으로 재산출할 수는 없다. 도구의 분위수 정의는 정렬 후 `ceil(n×q)−1` 인덱스다([코드](../../tools/profile_card_refresh.gd#L115)).
- 하드웨어·OS·빌드는 로그에 있는 범위까지만 확정한다. 당시 Mac은 엔진 로그의 **Apple M2**, Godot **4.7.2 Mono**, Metal **Forward Mobile**로 확인한다. 당시 macOS 세부 버전·RAM·전력 모드는 기록이 없다. 오늘 확인한 macOS 27.0.1/build26A434를 당시 환경으로 소급하지 않는다.

## 사례 1. 카드 불변 장식의 반복 생성을 제거한 warm 갱신 최적화

### 문제

전투 중 비용·설명·상태를 갱신할 때 카드의 스타일·그라디언트·원형 비용 배경·보석까지 다시 만들었다. 별도 벤치에서 카드 5장 갱신의 p50이 7.589ms로 관측됐다. 60Hz 프레임 예산 약16.67ms 중 상당한 구간이지만, 이 호출이 당시 402/604ms 정지의 단독 원인이라는 증거는 없다.

### 원인

`refresh()`가 텍스트와 불변 장식을 함께 갱신하는 구조를 확인했다. 원형 생성 함수의 전후 p50은 **0.882→0.880ms**로 거의 같았다. 생성 알고리즘 자체를 크게 가속한 것이 아니라 **필요 없는 재호출을 없앤 것**이라는 설명과 일치한다. 이 미세한 0.002ms 차이는 별도 성과로 삼지 않는다.

### 해결

영웅 팔레트·희귀도가 바뀌지 않으면 장식 갱신을 건너뛰고 텍스트·비용만 갱신한다. 비용/보석 텍스처를 키별 공유 캐시에 보관한다. 최대6팔레트·30조합이라는 값은 **[코드 산출/설계 상한]**이지 실제 생성 수·할당량 측정이 아니다.

### 결과

모두 **[당시 실측]**, 개선율은 **[이번 재계산]**이다.

| 카드 5장 warm 갱신 | 이전 | 이후 | 감소율 |
|---|---:|---:|---:|
| p50 | 7.589ms | 0.158ms | `(7.589−0.158)/7.589×100 = 97.9180%` |
| p95 | 9.857ms | 0.792ms | `(9.857−0.792)/9.857×100 = 91.9651%` |
| 표본 내 최대 | 11.604ms | 0.825ms | `(11.604−0.825)/11.604×100 = 92.8904%` |

p50 시간비는 `7.589/0.158 = 48.03`이다. **‘메서드 시간비 약48배’와 ‘시간97.92% 감소’는 같은 관측의 다른 표현이며, 게임 FPS48배 향상이 아니다.** 문장에는 시간 감소율을 권장한다.

### 측정 조건

- Apple M2 / macOS / Godot4.7.2 Mono / Metal Forward Mobile. 독립 에디터 실행 파일을 이용한 프로젝트 실행이며, export release 빌드 결과는 아니다.
- window·viewport1920×1080, visible·focused 모두 true로 전후 환경 JSON에 기록. 지속 포커스·OS 전체 부하까지 통제한 ABBA 교차 실험은 아니다.
- Cleopatra의 실제 시작 카드 앞5장, modern 카드 씬의 **REWARD 모드**. 실제 전투 손패 재구축 전체가 아닌 공통 `refresh()` 경로다.
- 초기 setup/refresh로 warm 상태를 만든 뒤, **전후 각20회 batch**. batch마다5장 갱신. 프로세스별 반복 세션은 확인되지 않는다.
- `Time.get_ticks_usec()`로 메서드 시작~반환 wall time 측정. 렌더 제출은 포함할 수 있지만 GPU 완료를 기다리지 않는다. Dummy audio, 격리 저장 사용.

## 사례 2. 동일 손패 갱신 시 카드 루트 생성·폐기 요청 제거

### 문제

같은 카드 Resource·같은 순서의 손패라도 갱신할 때마다 기존 카드 노드에 `queue_free()`를 호출하고5장을 다시 instantiate했다. 상태 변화 없이 중복 갱신돼도 노드 재생성이 발생했다. 당시에는 이 경로의 시간/생성 횟수 전후 벤치가 없어 ‘손패 재사용으로 몇ms 절약’이라는 주장은 만들 수 없었다.

### 원인

`afe1bee`의 `_refresh_hand()`는 항상 기존 배열을 비운 뒤 `_make_card()`를 호출한다. `1710ca6`에서는 순서·Resource 참조와 노드 유효성이 같으면 `setup()`·게이팅만 갱신하고 반환한다. 이 차이를 단순 코드 계산으로만 남기지 않고 오늘 실행해 확인했다.

### 해결

변하지 않은 손패는 루트를 재사용하되 비용·상태·튜토리얼 게이팅을 다시 적용한다. 카드 교체·순서 변경·프레임 디자인 변경은 재구축한다. 재사용한다고 갱신 자체를 생략하지 않는다.

### 결과 — 반드시 ‘오늘 신규 측정’으로 사용

**[오늘 신규 측정: 2026-10-22]** 최초 생성1회는 양쪽에서 제외했다.

| 고정5장·30회 재갱신 | 수정 전 컴포넌트 | 수정 후 컴포넌트 |
|---|---:|---:|
| 회당 새 카드 루트 | 매회5개 | 매회0개 |
| 합계 새 카드 루트 | 150개 | 0개 |
| 이전 루트의 삭제 대기 요청 합계 | 150개 | 0개 |
| 갱신 후 표시 루트 수 | 매회5개 | 매회5개 |

새 루트 생성 감소율=`(150−0)/150×100 = 100%`. 계측값은 호출 전후 instance ID와 이전 루트의 `is_queued_for_deletion()`이다. **전체 Node/메모리 할당량·즉시 해제 바이트·GC 시간은 아니다.** 새 루트0이라고 setup/텍스트 갱신 비용까지0인 것도 아니다. 처리 시간은 이번에 측정하지 않았다.

### 측정 조건

- Apple M2, 오늘 확인한 macOS27.0.1/build26A434, Godot4.7.2 Mono, headless/Dummy audio/Master mute.
- 변경 전 `afe1bee`와 변경 후 `1710ca6`에서 **`scenes/battle/battle_scene.gd`만** `git archive`로 별도 임시 경로에 추출. 다른 런타임 의존성은 두 arm 모두 **현재 e900b44 기반 작업 폴더의 동일 파일**을 사용했다. 옛 프로젝트 전체/옛 export 빌드 대조가 아니다.

### 포트폴리오 문장 초안

> AI 보조로 동일 손패의 카드 노드 재사용을 적용했다. 이후2026-10-22에 수정 전후 컴포넌트를 같은 격리 환경에서 검증하여, 고정5장 손패의30회 재갱신 중 새 카드 루트 생성과 기존 루트 삭제 대기 요청을 각각150회에서0회로 줄였음을 확인했다. 메모리 절감량이나 FPS 효과로 확대 해석하지 않았다.

## 사례 3. 난도 창을 유지하는 조우 이력 선택으로 반복 노출 감소

### 문제

액트 내 일반/정예 조합을 이력 없이 다시 뽑아 같은 조합이 반복 노출됐다. 단순히 몬스터 콘텐츠 수를 늘리는 대신 한 경로에서 기존 콘텐츠가 어떻게 선택되는지를 개선하는 문제다.

### 원인

선택기에 지난 조합·종 이력이 없었고, 실제15층 맵인데 일반 조우 진행도는9층 기준이었다. 대조군을 **기존 방식 /12층 가중치만 수정 /가중치+이력 적용**으로 나눴다. 가중치만 고쳐도 일반 반복은7,576→7,591로 줄지 않았으므로, 단순 층수 변경만으로 해결됐다는 설명을 배제할 수 있다.

### 해결

현재 난도 자격 창 안에서 직전 조합을 피하고, 조합 사용 횟수→종 사용 횟수가 적은 후보를 우선 선택한 뒤 동률에서 가중 랜덤을 사용한다. 풀 소진 때는 최소 사용 조합을 허용한다. 일반·정예·이벤트가 같은 이력을 쓰고 액트 전환·저장/불러오기에서도 이력을 보존한다. 같은 무리의 같은종 여러 마리와 여러 전투에 걸친 반복은 구분한다.

### 결과

**[당시 시뮬레이션]** 원본을 오늘 **개별 `sequence`의 정렬한 조합 키·직전 조합부터 재집계**해 아래 집계와 일치함을 확인했다. 재집계는 새 전투/새 조우 시뮬레이션이 아니다.

| 지표 | 기존 | 가중치만 수정 | 가중치+이력 |
|---|---:|---:|---:|
| 일반 조합 재등장 /27,774선택 | 7,576 | 7,591 | 833 |
| 같은 종류의 직전 일반 조합 반복 /27,774선택 | 4,595 | 4,275 | 0 |
| 정예 조합 재등장 /3,438선택 | 295 | 295 | 0 |

- 전체 변경의 일반 재등장 감소=`(7576−833)/7576×100 = 89.0048%`.
- 일반 재등장 비율=`7576/27774×100 = 27.2773%` → `833/27774×100 = 2.9992%`, **24.2781%p 감소**. ‘89%p 감소’가 아니다.
- 가중치 변경을 고정한 이력 선택의 대조=`(7591−833)/7591×100 = 89.0265%` 감소. 전후 두 변화가 섞였다는 점을 보완하는 내부 대조다.
- 표본의 직전 일반 반복은100% 감소했지만, 후보가 사실상1개면 실제 게임에서 반복이 불가피하다. 모든 경로의 반복0·최대2회라는 보장은 아니다.

## 추천과 분리하는 후보·사용 금지 주장

### A. 반복 캐릭터 아트 캐시 — 당시 숫자는 있으나 조건부 후보

- **문제/원인/해결:** 노드 해제 뒤 같은 PNG를 다시 읽는 경로 → 독립 텍스처 참조를 FIFO 캐시로 유지. `CharacterArtCache.get_texture()`와 영웅/적 호출부를 확인했다. 캐시24개는 설계 상한이지 MB 측정값이 아니다. 메모리가 늘 수 있다.
- **[당시 실측]** scarab의 첫 호출을 제외한4회 p50 **21.305→0.036ms**, 계산상99.8310% 감소. Cleopatra 생성5회 p50 **85.336→0.749ms**, 계산상99.1223% 감소이나 cold/warm 혼합 분포다. 이를 cold 로딩99% 감소로 쓰지 않는다.
- **조건 차이:** 전 JSON `window_focused=false`, 후 true. 각 단일 프로세스5회·warm scarab은4회뿐이고 raw 개별 시간 배열/OS 부하 통제가 없다. scarab **첫 호출은22.818→23.581ms로 개선되지 않음**, 서로 다른5개 아트 p50도21.347→21.725ms다. 반복 캐시 경로 효과라는 해석은 가능하나 전체/최초 로딩 개선의 증거가 아니다.
- **근거:** [전](../../log/campaign-bot/STSL-campaign-bot-f0MyjG/character-before.json)/[후](../../log/campaign-bot/STSL-campaign-bot-f0MyjG/character-after.json), [측정 스크립트](../../tools/profile_character_setup.gd#L87), [캐시](../../characters/character_art_cache.gd#L33). 구현4744e6b/main0a916bb(#237), 당시 미커밋1710ca6 기반. 파일별 빌드 SHA가 JSON에 없어 깨끗한 두 커밋 빌드 대조로 부르지 않는다.
- **기여/한계:** 사용자 도입 승인, AI 캐시 구현·벤치·검증. 개인 수작업 구현량은 미확인. 비교 조건이 더 강한 추천3개에 우선권을 줬으며 이 후보는 동일 포커스·자산·프로세스 순서 교차 반복을 추가하면 성능 중심 포트폴리오에서 대체 가능하다.

### B. 하트 텍스처 native polygon 검사 — 당시 소표본 조건부 후보

- **문제/원인/해결:** 64×64=4,096픽셀에서 GDScript ray casting을 호출하던 부분을 `Geometry2D.is_point_in_polygon`으로 교체. 4,096은 **코드상 검사 대상 수**이며 전체 할당량/실행 시간 수치가 아니다.
- **[당시 실측]** cold 텍스처 생성5회 p50 **14.103→7.300ms**, `(14.103−7.300)/14.103×100=48.2380%` 감소. 시간비1.93과 ‘93% 시간 감소’를 혼동하지 않는다. CPU 측 생성·제출 구간이지 GPU 시간 아님.
- **근거:** [전 JSON](../../log/campaign-bot/STSL-campaign-bot-f0MyjG/vfx-before.json)/[후 JSON](../../log/campaign-bot/STSL-campaign-bot-f0MyjG/vfx-after.json)의 `samples.textures.heart.cold`, [구현](../../scenes/vfx/gpu_particle_helpers.gd#L267), [cold 캐시 초기화 벤치](../../tools/profile_vfx_textures.gd#L101). 구현4744e6b/main0a916bb(#237). 픽셀/마스크 일치 검사는 정확성 보조 자료다.
- **조건/한계:** 같은 M2/Metal/mobile/1920×1080이나 전 focus=true·후 false. 다른 텍스처도 일부 크게 변동했고 개별 시간 배열/교차 반복이 없다. 따라서48.24%를 환경 독립적 개선으로 추천하지 않는다. 이 두 후보는 **기존 측정이 있는 사례**이며 오늘 다시 측정한 수치가 아니다. 사용자 문제 해결 승인, AI 원인 분석·교체·벤치 기여로 구분한다.

### C. 씬 로드·선택적 아트 준비 — 비용 이동과 총비용 감소 구분

- [당시 씬 보고서](../performance-scene-stutters-2026-10-11.md)에 첫 전투 교체499.199→4.720ms가 있으나 **시작 화면 warm466.246ms가 추가**된다. 총 로딩99% 단축으로 쓰지 않는다.

### D. 봇·자동화·오류 수정 — 유효한 개선과 규모 지표 구별

- [guard-v2](../game_design/guard_policy_v2_evaluation.md) 고정864상태의817→846승, [tempo-v3](../game_design/tempo_policy_evaluation.md)의503→535승은 **당시 전투 정책 실험 결과**다. 처리속도·사람의 게임 승률이 아니다. tempo-v3는 새패배2건으로 승격 게이트에 실패해 실험용이다. 회귀를 숨긴 ‘봇 완성’ 성과는 추천하지 않는다.

- 이전 오류의 관측 횟수·분모·수정 후 동등 노출이 없으면 오류 발생률0%/100% 개선을 만들지 않는다. 사용자 불편 제보·우선순위 결정과 AI 구현·실행 기여를 구별한다.

| 최초 로딩/end-to-end | 새 수치 미작성 | 시작 warm·선택 아트 준비·fade·ready·첫 실제 표시까지 같은 경계로 합산하는 전후 계측 필요. 기존 로그는 일부 구간/적 구성이 달라 총시간 대조 불가 |
| 반복 아트·하트 CPU | 과거 수치는 위 후보로 보존 | 포커스 동일·cold/warm 분리·같은 자산과 import 상태·여러 프로세스 ABBA 반복·개별 샘플 저장 시 추천 신뢰도 향상 가능 |
| 조작 단계·반복 작업 시간 | 적합한 전후 측정 없음 | 같은 사용 과제의 수동/자동 시간, 성공률, 입력 횟수, 반복 횟수 필요. 개발 대화 횟수나 테스트 개수를 사용자 조작 단계로 간주하지 않음 |

무자료 후보 중 현재 수정 전후 컴포넌트와 동일 시나리오를 안전하게 확보한 손패 생성 수는 실제 측정했다. 전체 게임 프레임·메모리·작업시간은 위 조건이 부족해 숫자를 보충하지 않았다. 과거 수치가 있는 후보의 통제 강화와 새로운 개선 실적 발견은 구별한다.

## 증거 보존·검산 메모

- `log/`와 사용자 Application Support의 JSON은 **Git ignored 로컬 산출물**이다. 다른 컴퓨터/공개 포트폴리오에서 링크만으로 접근되지 않는다. 제출 전 원본·측정 스크립트·필요한 소스 스냅샷을 별도 첨부하고, 개인정보·저작권·아트 재배포 범위를 확인해야 한다. 이 문서가 원본을 자동 Git 추적/업로드한 것은 아니다.
- 오늘 조우 시퀀스에서 일반/정예 분모·정렬 조합 키 재등장·직전 반복을 재집계해 표와 일치했다. 29개 기록 소스 SHA가 현재 파일과 일치했다. 비교 arm은 같은 평가기에서 실행한 정책 변형이지 old/new 바이너리2종이 아니다.
- 손패 harness는 기준/수정후 스크립트만 추출해 **현재 동일 의존성**에서 실행한 혼합 컴포넌트 실험이다. 임시 프로젝트는 원본 workspace로 체크아웃하지 않고 만들었고 실제 개인 저장은 사용하지 않았다. 현재 게임 동작 코드는 변경하지 않았다.
- 손패 실험을 재실행하려면 별도 프로젝트의 `baseline/scenes/battle/battle_scene.gd`와 `optimized/scenes/battle/battle_scene.gd`에 위 두 커밋의 파일을 각각 추출하고, 동일 현재 의존성을 연결한 뒤 보존한 harness를 root에 둔다. 복사된 `project.godot`의 custom user directory는 `STSL-tutorial-validation-portfolio-`로 시작해야 한다. **harness의 REPORT는 새 출력 경로로 변경하여 원본 결과를 덮어쓰지 않는다.** `Godot --headless --audio-driver Dummy --path <격리프로젝트> -s res://audit_hand.gd`로 실행한다.
- 정량 검산은 이번에 수행했고, 당시 성능 실험을 오늘 재실행한 것으로 쓰지 않았다. Git 커밋 Author만으로 수작업 기여를 확정하지 않았다.
